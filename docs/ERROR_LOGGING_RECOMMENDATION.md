# 錯誤紀錄與後台查詢建議（2026-10-30）

本方案已於 2026-10-30 實作。以下保留原始設計建議；實際欄位、收集範圍、權限、限制及測試請以 [錯誤紀錄管理實作與驗證](ERROR_LOGGING_IMPLEMENTATION.md) 為準。未實作的部署版本、WebGPU 能力／耗時欄位及嚴重度篩選不代表目前功能。

建議建立可供客服追查的「錯誤事件摘要」，詳細技術診斷保留在受限的 Workers Logs。不要將全部 console 輸出、每個成功 API 或任意 error.message 直接寫入業務資料庫。Workers Logs 支援 console 與結構化欄位查詢：[官方文件](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)。

## 建議最小欄位與操作

- 事件 ID／請求追蹤 ID、伺服器接收時間、來源（前台／後台／API／本機 AI）、功能／處理階段、白名單錯誤代碼、嚴重度、可讀中文說明、部署版本。
- 若已登入，從伺服器 session 推導用戶 ID，不信任客戶端自行聲稱的身分。客服可用用戶提供的公開 ID 或事件 ID 反查。
- 本機 AI 只傳模型 ID／固定版本、WebGPU 是否可用、下載／載入／辨識階段及耗時。語音、圖片、辨識結果、用戶輸入與草稿都不傳入 log。模型仍在用戶裝置推論；診斷事件傳送是一般 API，不是雲端 AI。
- 同類事件以來源＋功能＋白名單代碼＋版本作 fingerprint，累計次數、首次及最後發生時間，避免持續重試產生大量重複資料。
- 後台顯示時間、用戶 ID、功能、中文錯誤說明、次數、處理狀態，提供日期／功能／嚴重度／用戶 ID 篩選及分頁。客服先看可讀摘要，詳細診斷只讓適當管理權限查看。
- 建議獨立 errors.read／errors.write 權限；查看／結案操作另留稽核。建議初期保留 30 天並分批清理，再依實際支援需求調整，這是產品建議而非法律保留期限。

## 收集規則與可靠性

優先記錄保存失敗、未預期 API 5xx、公告工作失敗、本機模型下載／初始化／推論失敗。取消、必填欄位未填、一般查無結果不要當成程式錯誤；裝置不支援可另分類成相容性事件。前端送出的事件採白名單、限制長度／頻率並去重，避免任意字串、堆疊、URL query 或惡意資料進入紀錄。

密碼、token、Cookie、Authorization、資料庫連線字串、密鑰及私人內容不入 log。這也符合 [OWASP Logging Cheat Sheet 的敏感資料排除原則](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#data-to-exclude)。

錯誤寫入應與主要操作解耦並有時限；紀錄失敗不能使原本成功的保存變成失敗，更不能在同一個壞掉的資料庫反覆寫「資料庫失敗」。資料庫不可用時以平台日誌為保底，若增加佇列則限定重試與容量，不能無限累積。OWASP 也要求測試 logging 本身失敗不影響應用程式正常執行。

現有私密歷史查閱的稽核是另一種安全需求，仍維持「稽核寫入成功才回傳正文」；不要因錯誤事件採非阻塞而放寬這個既有規則。

若後續實作，至少測去除敏感資料、偽造用戶 ID、越權讀取、限流／去重、惡意換行與過長 payload、DB 中斷、記錄系統故障、到期清理，以及本機 AI 未上傳文字／媒體。
