# 前後台、產品與技術檢查

日期：2026-10-29。本次以現行本地程式、Docker PostgreSQL、Chrome 及建置輸出檢查；不是正式環境滲透測試或完整手機裝置認證。

## 已直接修正

| 問題 | 修正與影響 |
| --- | --- |
| 用戶 ID 藏在選單，不易提供客服 | 桌機及手機登入頁首直接顯示穩定 public_account_id，提供複製、成功回饋及失敗手動替代；沒有新增重複 profile API |
| 複製 fallback 失敗仍顯示成功 | 檢查 execCommand 結果；失敗顯示可手動複製，不謊報成功 |
| 前台選單鍵盤操作不完整 | Escape 關閉並回焦開啟按鈕；通知面板點外部關閉 |
| 複製成功文字使手機頁首跳動 | 視覺回饋顯示在原按鈕，額外播報僅供輔助工具 |
| 歷史完整內容讀取失敗停在讀取中 | 顯示錯誤及重試按鈕，不必關閉重開整個視窗 |
| 同條件搜尋無法觸發更新 | 加入重新載入序號，可重送相同查詢 |
| 超過最後一頁時總數變成 0 | 空白 offset 頁補查實際總數，保留正確分頁資訊 |
| 模型／權限切換遺失未保存變更 | 離開／切換或刷新時確認，取消保留修改；使用 beforeunload 保護整頁離開 |
| 設定 API 掛住造成後續 AI 共用 Promise 一起卡住 | 提示／模型讀取 15 秒逾時，清除進行中狀態，允許重試，保留手動功能 |
| 部署工具仍要求舊固定管理帳密且漏傳 pepper | 改為驗證／傳遞持久 ADMIN_PASSWORD_PEPPER，移除退役 NewebPay 環境要求；無遠端部署 |
| 公告 API 還接受退役付費受眾 | 新建／預覽只接受全部或指定用戶，不修改歷史受眾資料 |
| 客服說明與後台可讀歷史矛盾 | 移除「客服不會讀取紀錄」的錯誤保證，明確請提供用戶 ID 與問題描述 |
| 擴充元件上架文件與原始 manifest 過時 | 修正舊 host 網域、雲端圖片／SpeechRecognition 聲明；Dev／Prod 打包使用的 manifest 原已正確，未發佈商店 |
| 產品／技術文件仍要求雲端 AI、試用點數與方案 | 重寫現行產品、開發、部署、資料模型與退役政策；增補後台規範，歷史驗證結果獨立標註 |

## 檢查結果與效能觀察

- 最終 typecheck、lint、402 項測試（API 296／Web 84／Admin 22）、完整建置與 baseline guard 全部通過。

- 本次 Chrome：20 個前後台路由 × 1440／768／390／320 寬度，共 80 個畫面，未發現橫向溢出、JS 執行錯誤、失敗 API 或未標示表單。這是版面及載入檢查，不等同每個功能分支全覆蓋。
- 用戶 ID 在四種寬度可見，真實 clipboard 寫入／讀回一致；另模擬複製失敗確認替代提示。
- 實際瀏覽器驗證通知外部點擊、Escape 回焦、歷史 API 失敗後重試、模型與權限捨棄確認。
- 真實 Docker API 驗證空白分頁仍保留正確總數；退役公告受眾在單元測試拒絕且無寫入。
- 提示與模型共用進行中請求、使用 ETag 重新確認；新增逾時後重試回歸測試。
- 隔離驗證部署參數：pepper 必填且至少 32 字元，舊帳密及金流參數不再要求。沒有讀取正式密鑰或觸發部署。
- 本輪真實 Chrome／本地模型文字與貼圖解析、修改確認後寫入 Docker DB 共 5 項通過，無雲端推論呼叫。短語音於同日上一輪已真實驗證；本輪未重跑語音品質矩陣。
- 最近一次 build：Web 主 JS 約 326 kB（gzip 100 kB），Admin 主 JS 約 211 kB（gzip 67 kB）；後台頁面已分包，本地 AI Worker 約 556 kB。權重下載另計，主要首次等待仍在模型而非這些 JS 大小。
- 自動頁面檢查目前每頁約 2～4 個 API 請求；前台 profile 與通知平行讀取，新增用戶 ID 重用既有 profile。

## 後續建議（尚未實作）

| 優先 | 面向 | 建議與理由 |
| --- | --- | --- |
| 優先 | 裝置體驗／品質 | 建立桌機、Android、iPhone 的實機驗收表，涵蓋首次下載、GPU 不支援、低記憶體、中途取消、繁中圖片／語音、電量。WebGPU 可用不代表小模型品質或手機穩定已達標 |
| 優先 | 客服與隱私 | 歷史紀錄讀取新增管理者、用戶、時間、查詢目的稽核；目前主要管理寫操作有 audit，讀歷史尚未記錄。維持歷史查看獨立權限，正式上線前明確訂存取政策 |
| 優先 | 回饋閉環 | 讓用戶查看自己的回饋編號／處理狀態，客服可由回饋跳到已篩選的用戶列表；目前送出後只有成功提示，往返較多 |
| 次要 | 資料查詢 | 用戶列表 COUNT OVER 會計算所有符合列，深 offset 與名稱 ILIKE 搜尋在大資料量可能變慢。以代表性數據 EXPLAIN 後評估計數策略、游標分頁、名稱搜尋索引；不是現在無證據全面加索引 |
| 次要 | 保存歷史 | 目前 author_user_id／input_type 索引與作者加 id 倒序的查詢不完全相同；大量作者歷史可評估 (author_user_id,id DESC)，驗證查詢計畫後再同步 schema／基線 |
| 次要 | 管理帳號 | 帳號管理 API 目前最多 100 筆且沒有完整分頁，達到規模前補搜尋／分頁／總數，避免較舊帳號無法操作 |
| 次要 | 表單體驗 | 角色名稱與多張帳號卡片同時修改仍需更一致的未保存標記／整頁保護；本輪先補模型及權限最容易遺失的流程 |
| 次要 | 模型設定 | 增加套用前小型測試、格式／實測品質標籤及下載大小說明。現在只有相容性驗證；切小模型不保證繁中辨識品質 |
| 次要 | 可維護性 | 將密集的管理 TSX／管理路由依列表、表單、資料存取分拆並統一格式；避免每次微調都碰整段單行程式。API 錯誤應統一 request ID，便於客服反查 |
| 次要 | 路由命名 | /subscription 目前實際是本機 AI，後續改成 /local-ai 並保留舊路由轉址；同時避免把產品沒有的方案概念帶回介面 |

不建議為減少一次 DB 查詢而長時間快取管理權限，否則停用或移除權限不能即時生效。也不建議把本機 AI 失敗改成雲端備援，這與產品決策衝突。
