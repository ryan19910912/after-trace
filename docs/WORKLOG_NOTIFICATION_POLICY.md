# AFTERTRACE Notification Policy

Durable product/development contract for AFTERTRACE notifications.

## Notification categories

Customer-facing notifications use exactly three primary categories for the current product:

- `ANNOUNCEMENT` / 公告通知 — operator/admin-authored communication such as maintenance windows, release notices or service announcements.
- `SYSTEM` / 系統通知 — deterministic product/business events such as payment success, subscription activation/renewal/cancellation or AI plan limit state.
- `TASK` / 待辦通知 — reminders derived from the user's own AFTERTRACE task/reminder data.

Security-related events may stay under `SYSTEM` initially. A separate security category is unnecessary until a concrete product need appears.

## Delivery channels

Notification category and delivery channel are separate concepts.

Current channels:

- `IN_APP` — durable notification-center item inside Web/PWA;
- `PUSH` — Web Push / PWA push notification when the user has granted permission and a valid subscription exists.

A notification may use one or both channels. Future channels such as email must be additive and must not require redefining the three product categories.

## Notification center

Authenticated Web/PWA exposes a notification bell in the top-right account area.

The bell should expose unread count and open an in-product notification center. Items display at minimum:

- category;
- title;
- body/summary;
- created/sent time;
- read/unread state;
- optional safe deep-link target.

`read_at` is durable. Push delivery failure must not remove the durable IN_APP item when the product event is meant to remain visible.

## ANNOUNCEMENT / 公告

Announcements are created from Admin.

Initial Admin capability:

- create announcement title/body;
- select audience;
- select delivery channels;
- send immediately or set `scheduled_at`;
- preview before send;
- cancel a still-pending scheduled announcement;
- inspect status such as DRAFT / SCHEDULED / SENDING / SENT / CANCELLED / FAILED;
- inspect high-level recipient/delivery counts where available.

Initial audience options:

- `ALL_USERS`;
- `FREE_USERS`;
- `AI_SUBSCRIBERS`;
- `SPECIFIC_USERS`.

Example: `今晚 23:00～23:15 進行系統更新` may be sent to all users through IN_APP + PUSH.

V1 needs one scheduled send time per announcement. Do not build a multi-step marketing campaign engine.

## SYSTEM / 系統通知

System notifications are normally generated by deterministic backend events rather than manually authored messages.

Examples:

- payment succeeded;
- subscription activated;
- subscription renewed;
- subscription cancelled / period ending;
- AI monthly resource limit reached.

Each event-driven system notification must have a durable idempotency/event key or equivalent uniqueness boundary so webhook/event retry cannot create duplicate customer notifications.

Admin may inspect system notifications. Manual Admin sending should default to ANNOUNCEMENT; do not pretend an arbitrary Admin message is a real payment/subscription SYSTEM event.

## TASK / 待辦通知

Task notifications originate from durable user tasks/reminders.

- reminder time is deterministic stored data;
- AI may interpret a natural-language time only as a proposal;
- user confirms the task/reminder before it becomes durable;
- task reminder delivery is idempotent;
- a task notification may deep-link back to the related task/Record when authorized.

Target scheduler:

- one Cloudflare Worker scheduled handler/Cron for the system, approximately every 5 minutes;
- bounded due-row query;
- idempotent delivery state;
- no one-Cron-per-task design;
- Cloudflare Queue is optional later when fan-out/volume justifies it.

## Push subscriptions

Push subscription data is per authenticated user/device/browser installation and is not the user's account identity.

Persist sufficient Web Push subscription data such as:

- endpoint;
- `p256dh` key;
- `auth` secret;
- user/device/browser metadata useful for support;
- created/updated timestamps;
- revoked/invalidated timestamp;
- last successful delivery timestamp where useful.

Expired or permanently invalid push subscriptions must be revocable/disabled without affecting the account or IN_APP notifications.

## iOS / iPadOS PWA push

AFTERTRACE must support the Home Screen PWA push path on supported iOS/iPadOS versions.

Product/UX rules:

- the user first adds AFTERTRACE to the Home Screen;
- notification permission is requested only after an explicit user action such as `開啟通知`;
- do not request notification permission automatically on initial page load;
- if permission is denied or unsupported, IN_APP notifications still work;
- the app must not claim that a normal Safari tab alone has the same push behavior as an installed Home Screen PWA;
- push is an enhancement, not the durable source of truth.

Android/desktop PWA use the same Web Push domain model where supported.

## Notification preferences

V1 preference controls may stay small:

- announcement PUSH may be disabled by the user;
- task PUSH may be disabled by the user;
- system PUSH may be configurable where appropriate;
- required durable transaction/account SYSTEM messages may still remain visible IN_APP even when PUSH is disabled.

Do not let a push preference delete durable notification history.

## Admin manual send safety

Before an Admin manual announcement is sent:

- show audience/channel/schedule preview;
- require explicit send confirmation;
- do not silently broaden `SPECIFIC_USERS` to all users;
- persist actor/admin identity and timestamps for audit;
- scheduled sends remain cancellable until dispatch starts;
- retries must not duplicate recipients.

## Architecture boundary

Notifications are a shared product service used by announcement, system and task domains.

Preferred flow:

`Domain/Admin event -> Notification Service -> durable IN_APP recipient state -> optional PUSH delivery`

Do not tie notification type to LINE OA. LINE OA remains an external customer-support channel and is not a notification transport for this product plan.

GitHub Actions must not be used as validation unless explicitly requested by the user.
